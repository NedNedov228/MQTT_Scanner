# Как самостоятельно проверить MQTT Security Scanner

Инструкция для macOS. Все команды выполняются в Terminal из папки проекта.
Сканер проверяет один выбранный MQTT-порт. Лаборатория создаёт семь локальных
брокеров с заранее известными настройками, поэтому результат можно сравнить
с ожидаемым, а не просто убедиться, что программа запускается.

## 1. Подготовить окружение

```sh
cd /Users/nednedov/Documents/Programmierung/MQTT_Scanner
open -a Docker
```

Дождитесь запуска Docker Desktop, затем выполните:

```sh
docker info
.venv/bin/python --version
.venv/bin/mqtt-scanner --help
```

`docker info` должен показать информацию о сервере без ошибки подключения.
Версия Python должна быть 3.12 или новее. Последняя команда должна вывести
справку с подкомандой `check`.

В текущей рабочей папке окружение `.venv` уже подготовлено. При установке из
нового клонирования репозитория создайте его отдельно:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
```

## 2. Запустить лабораторию

```sh
make lab-up
docker compose -f lab/compose.yaml ps
```

Ожидается семь работающих контейнеров: `anonymous`, `password`, `tls`,
`wrong-host`, `expired`, `acl-secure`, `acl-open`. Порты 18830–18836 опубликованы
только на `127.0.0.1`. Команда `make lab-up` пересоздаёт стенд и его тестовые
сертификаты и пароли.

Если контейнер завершился или не отвечает, сначала посмотрите его журнал:

```sh
docker compose -f lab/compose.yaml logs --tail=50
```

Ошибка `address already in use` означает, что указанный порт занят другим
процессом. Ошибка подключения к Docker обычно означает, что Docker Desktop
ещё не запущен. До устранения ошибки стенда результат сканирования не проверяет
нужный сценарий.

## 3. Проверить намеренно небезопасный брокер

```sh
.venv/bin/mqtt-scanner check localhost --port 18830 --output reports/anonymous
echo $?
```

Ожидаемый код выхода — `1`. Здесь это означает найденные проблемы, а не сбой
программы. Команду `echo $?` вводите сразу после сканирования: любая другая
команда изменит сохранённый код выхода.

| Проверка | Ожидаемый результат | Почему |
| --- | --- | --- |
| `network.reachability` | PASS | TCP-порт доступен |
| `transport.tls` | FAIL, HIGH | Получен ответ MQTT без шифрования |
| `protocol.mqtt` | PASS | Получен корректный MQTT CONNACK |
| `auth.anonymous` | FAIL, HIGH | Подключение без логина и пароля принято |

Программа напечатает полные пути к двум готовым файлам. Откройте HTML:

```sh
open reports/anonymous/report.html
```

В браузере должны быть `localhost:18830`, дата сканирования, сводка
`2 policy failures`, `0 errors`, `0 inconclusive` и четыре карточки проверок.
Время отчёта записывается в UTC (`+00:00`), поэтому оно может отличаться от
местного времени.

Внутренний файл `src/mqtt_scanner/templates/report.html.j2` — заготовка для
генератора. Если видны `{{ report.target.host }}` или `{% for ... %}`, открыт
этот шаблон либо его копия. Открывать нужно `report.html` именно из каталога,
переданного через `--output`. Браузер сам не выполняет Jinja-шаблоны.

Если сканирование завершилось до создания отчёта, старый файл мог остаться на
диске. Всегда сравнивайте дату внутри отчёта с текущим запуском и проверяйте,
что программа напечатала пути к результатам.

## 4. Проверить брокер с корректным TLS

```sh
.venv/bin/mqtt-scanner check localhost --port 18832 --transport tls \
  --ca-file lab/generated/ca.pem --output reports/tls
echo $?
open reports/tls/report.html
```

Ожидается код `0`, четыре PASS и нулевая сводка проблем. Сканер должен подтвердить
доверие к сертификату, имя `localhost`, срок действия сертификата и отказ
анонимному клиенту. `CONNACK code 5: not authorized` здесь ожидаем: брокер
требует аутентификацию, и это соответствует выбранной политике.

Используйте `localhost`, а не `127.0.0.1`: сертификат стенда выписан на имя
`localhost`. Параметр `--ca-file` нужен, потому что лабораторный CA не установлен
в системное хранилище доверия.

PASS относится к выполненной проверке. Этот результат не подтверждает
отсутствие любых возможных уязвимостей брокера и не проверяет его ACL.

## 5. Проверить отрицательные сценарии

Пароль требуется, но шифрования нет:

```sh
.venv/bin/mqtt-scanner check localhost --port 18831 --output reports/password
echo $?
```

Ожидается код `1`: `auth.anonymous` — PASS, `transport.tls` — FAIL.
Так можно убедиться, что сканер оценивает аутентификацию и шифрование отдельно.

Сертификат с неверным именем:

```sh
.venv/bin/mqtt-scanner check localhost --port 18833 --transport tls \
  --ca-file lab/generated/ca.pem --output reports/wrong-host
echo $?
```

Ожидается код `1`, TLS — FAIL с причиной `Hostname mismatch`.
Проверки MQTT и анонимного доступа — SKIPPED: сканер не продолжает соединение
с неподтверждённым сертификатом.

Просроченный сертификат:

```sh
.venv/bin/mqtt-scanner check localhost --port 18834 --transport tls \
  --ca-file lab/generated/ca.pem --output reports/expired
echo $?
```

Ожидается код `1`, TLS — FAIL с причиной `certificate has expired`,
MQTT и анонимный доступ — SKIPPED.

Отсутствие доверия к лабораторному CA:

```sh
.venv/bin/mqtt-scanner check localhost --port 18832 --transport tls \
  --output reports/untrusted
echo $?
```

Без `--ca-file` ожидается код `1` и ошибка проверки доверия. Это ожидание
предполагает, что вы не добавляли CA стенда в системное хранилище вручную.

Ошибочно выбранный TLS на обычном MQTT-порту:

```sh
.venv/bin/mqtt-scanner check localhost --port 18831 --transport tls \
  --timeout 1 --deadline 6 --output reports/wrong-transport
echo $?
```

Ожидается код `3`: TLS — UNKNOWN, поскольку TLS handshake не завершился.
Сканер не должен на основании одной этой ошибки утверждать, что брокер
вообще не поддерживает TLS, или автоматически переходить к обычному TCP.

## 6. Запустить автоматические тесты

Пока лаборатория работает, выполните:

```sh
MQTT_LAB=1 .venv/bin/pytest -q
```

Для этой версии ожидается **43 passed**, без `failed` и `skipped`.
`MQTT_LAB=1` делает недоступный стенд ошибкой: тесты не смогут незаметно
пропустить интеграционные проверки.

Тесты проверяют реальные брокеры, доверие и ошибки сертификатов, тайм-ауты,
повреждённые MQTT-ответы, завершение дочерних процессов, HTML-экранирование,
содержимое отчётов и коды выхода. Отдельные обычные Paho-клиенты проверяют
настройки лаборатории, в том числе фактическую доставку сообщений при
разрешённых и запрещённых операциях. Сам сканер сообщений не публикует.

При необходимости можно повторить проверки разработки:

```sh
.venv/bin/ruff check src tests lab/setup.py
.venv/bin/ruff format --check src tests lab/setup.py
.venv/bin/mypy src tests lab/setup.py
.venv/bin/pip-audit
.venv/bin/python -m build
```

Аудит зависимостей проверяет известные уязвимости на момент запуска. Локальный
неопубликованный пакет `mqtt-security-scanner` база PyPI пропускает; его код
проверялся отдельно через Codex Security.

## 7. Посмотреть JSON и проверить недоступный брокер

Для просмотра структурированных данных:

```sh
.venv/bin/python -m json.tool reports/anonymous/report.json
```

Внутри должны быть версия схемы, адрес, порт, время, политика и массив
`findings` из четырёх проверок. Значения должны совпадать с HTML-отчётом
из того же каталога.

Теперь остановите стенд и проверьте обработку недоступного адреса:

```sh
make lab-down
.venv/bin/mqtt-scanner check localhost --port 18830 \
  --timeout 1 --deadline 6 --output reports/offline
echo $?
```

Ожидается код `2`, `network.reachability` — ERROR, остальные проверки — SKIPPED.
Недоступный брокер не должен получать результат «всё безопасно».

Для нового сеанса снова выполните `make lab-up`. Сочетание положительных,
отрицательных сценариев и автоматических тестов подтверждает заявленное
поведение MVP в вашей среде; абсолютную гарантию для всех серверов оно не даёт.
